#+TITLE: SGLang vs vLLM
#+DATE: 2026-01-08
#+SUMMARY: A comparison of the two dominant open-source LLM inference engines: architecture, key components, performance benchmarks, industry adoption, and decision criteria.

* 1. Overview

Both SGLang and vLLM are high-performance, open-source inference engines for serving large language models. They share a lineage: both came out of UC Berkeley research labs, and both have grown quickly into production systems behind some of the world's largest AI deployments. They take different architectural approaches to the same problem, which is making LLM inference fast, efficient, and cost-effective.

** SGLang (Structured Generation Language)

SGLang co-designs a frontend DSL with a backend runtime. Its core innovation is *RadixAttention*, a radix-tree-based KV cache manager that shares prefixes across requests automatically and at fine granularity. It also has a zero-overhead CPU scheduler, a cache-aware load balancer, and a compressed FSM for structured outputs. It is optimized for multi-turn, agentic, and structured workloads.

- Origin: LMSYS Org (Lianmin Zheng, Ying Sheng)
- First release: Jan 2024
- GitHub stars: ~20k+ (as of early 2026)
- Hosted by: LMSYS (PyTorch ecosystem)

** vLLM (Virtual Large Language Model)

vLLM pioneered *PagedAttention*, an OS-inspired virtual memory system for KV cache management. It focuses on maximum hardware compatibility, broad model support, and stability for enterprise use. Its plugin-based architecture supports many backends, quantization formats, and hardware targets. By install base, it is the most widely adopted OSS inference engine.

- Origin: UC Berkeley (Woosuk Kwon)
- First release: Jun 2023
- GitHub stars: ~50k+ (as of early 2026)
- Hosted by: PyTorch Foundation (via LF AI)

* 2. Architecture comparison

Both engines aim to maximize GPU utilization for LLM serving, but their design philosophies differ. SGLang co-designs the programming interface with the runtime to optimize structured, multi-step generation workflows. vLLM aims to be a modular, pluggable inference engine with the broadest possible compatibility.

*** SGLang inference dataflow

#+begin_src mermaid
sequenceDiagram
    participant Client
    participant Router as sgl-router<br/>(Rust LB)
    participant Scheduler as Scheduler<br/>(Zero-overhead)
    participant Radix as RadixAttention<br/>KV Cache
    participant GPU as GPU Workers<br/>(FlashInfer)

    Client->>Router: 1. Send request
    Router->>Router: 2. Predict cache hit rate
    Router->>Scheduler: 3. Route to best instance
    Scheduler->>Radix: 4. Radix tree prefix lookup
    Radix-->>Scheduler: 5. Return matched KV nodes

    Note over Scheduler,GPU: Zero-overhead: prepare next batch while GPU runs

    Scheduler->>GPU: 6. Submit batch (overlapped)
    GPU->>GPU: 7. Execute FlashInfer attention
    GPU->>GPU: 8. Decode tokens (+ xGrammar jump-forward)
    GPU-->>Scheduler: 9. Return generated tokens
    Scheduler->>Radix: 10. Insert new KV cache nodes
    Scheduler-->>Client: 11. Stream tokens
#+end_src

How a request moves through SGLang:

1. Cache-aware routing (steps 1-3): The Rust-based sgl-router predicts which backend instance will have the highest cache hit rate for the request's prefix. This gives up to 3.8x higher hit rates than round-robin.

2. Radix tree lookup (steps 4-5): The scheduler walks the radix tree to find the longest matching prefix. It finds shared prefixes (system prompts, few-shot examples) automatically, with no configuration.

3. Zero-overhead scheduling (step 6): While the GPU processes the current batch, the CPU prepares the next one. This overlap removes the CPU scheduling stalls that can waste up to 50% of time in other engines.

4. Execution with jump-forward (steps 7-8): FlashInfer kernels run attention. For structured output, xGrammar's compressed FSM can skip deterministic tokens entirely, bypassing 30-50% of GPU forward passes.

5. Cache update and streaming (steps 9-11): New KV cache goes into the radix tree for later reuse, and tokens stream back to the client as they're generated.

    participant GPU as Executor<br/>(Model Runner)

    Client->>API: 1. Send request
    API->>API: 2. Tokenize input
    API->>Engine: 3. Queue request
    Engine->>Block: 4. Allocate logical blocks
    Block->>Block: 5. Check prefix cache (APC)
    Block-->>Engine: 6. Return block allocation

    loop Continuous Batching (per iteration)
        Engine->>Engine: 7. Dynamic batch formation
        Engine->>GPU: 8. Execute with block tables
        GPU->>GPU: 9. Attention via indirection
        GPU-->>Engine: 10. Return logits
        Engine->>Engine: 11. Sample next token
        Engine->>Block: 12. Append to blocks (CoW if shared)
        Block->>Block: 13. Check memory pressure
        alt Memory pressure high
            Block->>Block: 14. Preempt / swap to CPU
        end
    end

    Engine-->>Client: 15. Stream tokens
#+end_src

How a request moves through vLLM:

1. Request handling (steps 1-3): The API server tokenizes the input and queues the request in the core engine. vLLM's OpenAI-compatible API is the most mature in the ecosystem.

2. Block allocation (steps 4-6): The block manager allocates logical blocks for the sequence. As in OS virtual memory, blocks are fixed size (typically 16 tokens) and mapped to physical GPU memory on demand. Automatic Prefix Caching (APC) checks for reusable prefixes.

3. Continuous batching loop (steps 7-12): Each iteration forms a batch from all active requests. The GPU executes attention through block table indirection, so physical blocks don't need to be contiguous. New tokens are appended, and if blocks are shared, copy-on-write creates new physical blocks.

4. Memory management (steps 13-14): Under memory pressure, vLLM can preempt lower-priority requests and either swap their KV cache to CPU memory or recompute it later. This is how it copes with bursty workloads.

5. Streaming (step 15): Tokens stream back as they're generated, and the loop continues until all sequences complete.

* 3. KV cache management: the core differentiator

The KV cache is the largest memory consumer during LLM inference, and how each engine manages it is perhaps its single most important architectural decision. Both try to eliminate memory waste and enable sharing, but they use very different data structures and make different trade-offs.

** SGLang: RadixAttention (radix tree)

SGLang stores KV cache tensors in a *radix tree* (compressed trie) whose edges are labeled with variable-length token sequences. Prefix sharing across all requests happens automatically and at fine granularity, with no manual configuration.

How it works:

1. When a new request arrives, the system traverses the radix tree matching token-by-token
2. Shared prefixes (e.g., system prompts) are found automatically
3. Only divergent suffixes need computation
4. An LRU eviction policy recursively removes leaf nodes when memory is full

#+begin_example
                    ┌─────────────────────────┐
                    │  "You are a helpful..." │  ← Shared prefix
                    │   (KV cache computed    │    (computed ONCE)
                    │    once, reused)        │
                    └──────────┬──────────────┘
                   ┌───────────┼───────────────┐
                   ▼           ▼               ▼
         ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
         │ "What is     │ │ "What is     │ │ "Explain     │
         │  Python?"    │ │  JavaScript?"│ │  recursion"  │
         └──────┬───────┘ └──────┬───────┘ └──────┬───────┘
                ▼                ▼                ▼
         [output A]       [output B]       [output C]

    Only the unique suffixes need fresh computation!
#+end_example

The cache is dynamic and content-addressable, so the system "learns" caching patterns from actual traffic. It handles branching conversations, few-shot examples, agentic loops, and tree-of-thought workloads automatically, which makes it a good fit for multi-turn chat, shared system prompts, RAG with common prefixes, and agentic workflows with branching.

** vLLM: PagedAttention (virtual memory paging)

vLLM breaks the KV cache into fixed-size *blocks* (typically 16 tokens each) that can sit non-contiguously in GPU memory. A block table maps logical blocks to physical blocks, an idea taken directly from OS virtual memory.

How it works:

1. Each request maintains a block table (like a page table)
2. Blocks are allocated on demand, not pre-reserved
3. When sequences share a prefix, their block tables point to the same physical blocks
4. Copy-on-write handles divergence
5. Blocks can be swapped to CPU or recomputed under memory pressure

#+begin_example
    Request A                    Physical GPU Memory
    ┌──────────────┐             ┌─────────────┐
    │ Logical Blk 0│──────────►  │ Phys Blk  7 │  ← shared prefix
    │ Logical Blk 1│──────┐      │ Phys Blk  1 │  ← shared prefix
    │ Logical Blk 2│──┐   │      │ Phys Blk  3 │  ← A's unique tokens
    └──────────────┘  │   │      │ Phys Blk  5 │  ← B's unique tokens
                      │   │      │ (free)      │
    Request B         │   │      │ (free)      │
    ┌──────────────┐  │   │      └─────────────┘
    │ Logical Blk 0│──┼───┘
    │ Logical Blk 1│──┘           Blocks stored
    │ Logical Blk 2│──────────►   NON-CONTIGUOUSLY
    └──────────────┘              (like OS pages)
#+end_example

Memory waste is near zero (under 4%, vs 60-80% in traditional systems), and it works consistently across all hardware backends and model types. It suits predictable workloads, batch inference, templated prompts, beam search, and setups that need broad hardware support.

** Practical impact

#+begin_quote
Say you have 100 requests sharing a 500-token system prompt:

- A traditional system computes 50,000 tokens.
- RadixAttention (SGLang) computes 500 tokens once and reuses them 99 times automatically, with zero configuration.
- APC (vLLM) gives similar savings, but works best when you can predict and structure your caching patterns.

The savings compound with few-shot prompting, RAG pipelines, and multi-turn conversations.
#+end_quote

* 4. Scheduler design

The CPU scheduler is a surprisingly serious bottleneck in LLM inference. On every iteration the CPU decides which requests to batch, allocates memory, handles prefix matching, and prepares metadata, all while the GPU waits. How each engine handles this overhead accounts for a good part of the performance gap between them.

** SGLang: zero-overhead scheduler

SGLang's scheduler runs *one batch ahead* of the GPU: while the GPU processes the current batch, the CPU prepares the next one, so scheduling work overlaps with GPU computation.

#+begin_example
  TRADITIONAL (Sequential):

  ┌──────────┐ ┌────────────────────┐ ┌──────────┐ ┌────────────────────┐
  │ CPU sched│ │    GPU batch 1     │ │ CPU sched│ │    GPU batch 2     │
  └──────────┘ └────────────────────┘ └──────────┘ └────────────────────┘
   GPU idle ↑                          GPU idle ↑


  SGLANG (Overlapped):

  ┌──────────┐
  │CPU prep 1│
  └────┬─────┘
       │  ┌──────────┐
       │  │CPU prep 2│
       │  └────┬─────┘
       │       │  ┌──────────┐
       │       │  │CPU prep 3│
  ┌────┴───────────────┐     │
  │    GPU batch 1     │     │
  └────────────────────┤     │
       ┌───────────────┴─────────────┐
       │       GPU batch 2           │
       └─────────────────────────────┤
              ┌──────────────────────┴───────────┐
              │         GPU batch 3              │
              └──────────────────────────────────┘

  → No GPU idle time! CPU scheduling is fully hidden behind GPU work.
#+end_example

Profiling shows unoptimized engines spend *up to 50% of time on CPU overhead*. SGLang cuts this to near zero, for a measurable 1.1-1.3x throughput improvement. The effect is largest with small models and large tensor parallelism, where GPU steps are fast and CPU stalls cost proportionally more.

** vLLM: V1 engine scheduler

vLLM's V1 engine (released 2025) is a full re-architecture. It uses *dynamic scheduling with preemption support*, so it can pause lower-priority requests and offload their KV cache to CPU memory when GPU memory is tight.

The V1 scheduler favors flexibility and correctness over raw scheduling speed. It supports guided decoding, speculative decoding, and prefix caching within the same scheduling loop. The cost is somewhat higher per-step overhead than SGLang's heavily optimized pipeline.

* 5. Structured output generation

Production applications increasingly need guaranteed-valid structured outputs (JSON, XML, SQL). Both engines support constrained decoding, but SGLang has invested more heavily in it.

** SGLang: compressed FSM + jump-forward decoding

SGLang compiles output schemas (e.g., Pydantic models) into a *compressed finite state machine*. When the FSM knows the next token deterministically (like =:= after a JSON key), SGLang skips the GPU and inserts the token directly. For highly structured outputs, this "jump-forward" technique can bypass *30-50% of generation steps*.

With the xGrammar backend, SGLang decodes JSON up to *10x faster* than other open-source solutions.

#+begin_example
  Schema: { "name": str, "age": int }

  Standard decoding:     GPU → "{" → GPU → '"' → GPU → "n" → GPU → "a" → ...
                         (every token goes through the model)

  Jump-forward:          GPU → "name" → SKIP '{"' → GPU → value → SKIP '","age":' → GPU → value → SKIP "}"
                         (deterministic tokens inserted directly, no GPU call)

  Result: 30-50% fewer GPU forward passes for structured output
#+end_example

** vLLM: guided decoding via plugins

vLLM supports constrained decoding through its pluggable architecture, with xGrammar and Outlines as backends. It applies token-level masks that restrict the model's vocabulary at each step. This works, but it runs as an overlay on the standard pipeline and isn't deeply integrated into the scheduling and caching system.

* 6. Distributed serving & multi-GPU

Both engines support tensor, pipeline, and data parallelism. Where they differ is load balancing and cache-aware routing at scale.

| Strategy                   | SGLang                                                                            | vLLM                                                                           |
|----------------------------+-----------------------------------------------------------------------------------+--------------------------------------------------------------------------------|
| *Tensor Parallelism*       | Full support; optimized for high-TP with zero-overhead scheduling                 | Full support; zero-redundancy memory allocation                                |
| *Data Parallelism*         | DP attention for DeepSeek models (1.9x decode throughput); sgl-router coordinates | Standard DP; llm-d project for K8s-native scaling                              |
| *Expert Parallelism*       | Native EP for MoE models; large-scale EP on 96+ H100 GPUs demonstrated            | MoE support with expert-level load balancing                                   |
| *Pipeline Parallelism*     | Supported for multi-node deployments                                              | Multi-node scaling via PP across servers                                       |
| *Prefill-Decode Disagg.*   | Native support                                                                    | Via llm-d project (Red Hat, Google, IBM, NVIDIA)                               |
| *Load Balancing*           | sgl-router: Rust, predicts cache hit rates (3.8x higher hit rate)                 | llm-d: K8s Inference Gateway + LMCache                                         |

vLLM has the edge on hardware breadth. Its plugin architecture supports more hardware, including AWS Neuron and Intel Gaudi, which matters for organizations committed to non-NVIDIA stacks. SGLang leads on optimization for cutting-edge NVIDIA hardware (GB200, large-scale EP) and has been closing the gap.
#+end_quote

* 9. TL;DR decision guide

Neither engine is universally "better". The right choice depends on your workload, team capabilities, hardware, and priorities.

** Choose SGLang when...

1. *Multi-turn conversations with shared context*, such as chatbots, coding assistants, and tutoring systems. RadixAttention shares KV cache across conversational turns automatically, with zero configuration.

2. *Structured output generation (JSON, XML, SQL).* Compressed FSM + jump-forward decoding can skip 30-50% of generation steps, and JSON tasks run up to 10x faster.

3. *Agentic / tree-of-thought / reasoning workloads.* Branching execution paths fit the radix tree cache naturally, and the frontend DSL makes complex LLM programs composable.

4. *Maximum throughput on NVIDIA H100/GB200.* Independent benchmarks consistently show a 15-30% throughput advantage on Hopper-class GPUs.

5. *RL post-training / rollout generation.* SGLang is the de facto backbone for RL frameworks (verl, AReaL, Miles), with native integrations for training workflows.

** Choose vLLM when...

1. *Broad hardware compatibility is critical.* If you need AMD, Intel Gaudi, AWS Trainium, TPU, and NVIDIA, vLLM has the widest hardware backend support.

2. *Enterprise-grade stability & support.* Red Hat AI Inference Server is a commercial, hardened distribution, and vLLM has the largest community, the most tutorials, and the most battle-testing in the Fortune 500.

3. *Drop-in OpenAI API replacement.* vLLM's OpenAI-compatible API is the most mature, so migrations have little friction.

4. *K8s-native distributed deployment.* The llm-d project provides production-grade K8s orchestration with disaggregated serving.

5. *Batch inference with predictable patterns*, such as templated prompts, batch content generation, and single-round Q&A. PagedAttention does well when caching patterns are consistent.

** Either works well for...

- *Standard chat serving, RAG pipelines, general-purpose LLM APIs.* Both are production-grade, and the performance differences narrow with each release.
- *DeepSeek, Llama, Qwen, Mistral model families.* Both have day-0 support for major releases, and both support FP8, INT4, AWQ, and GPTQ quantization.
